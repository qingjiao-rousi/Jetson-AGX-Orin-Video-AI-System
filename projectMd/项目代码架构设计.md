# 项目代码架构设计

## 1. 设计目标

本项目采用 `Python 主控 + 少量 C/C++ 插件` 的实现方式，整体遵循 `分层架构 + 高解耦 + 易扩展` 的设计原则。

目标有 4 个：

1. 代码结构清晰，便于阅读、维护和二次开发
2. 模块职责单一，降低 DeepStream、Web、输出模块之间的耦合
3. 既保留工程化深度，又适合面试时快速讲清楚系统设计思路
4. 支持后续继续扩展优化策略、输出方式和监控能力

---

## 2. 总体架构思路

项目采用 `分层单体 + 插件式扩展` 架构。

- `分层单体`
  指部署时先保持为单机单服务，避免一开始就把项目拆成多个进程或微服务，降低复杂度。
- `插件式扩展`
  指把 DeepStream 自定义后处理、输出通道、优化策略做成可替换模块，后续扩展时不需要重写主流程。

整体职责划分如下：

1. `entry/bootstrap`
   负责程序启动、配置加载、日志初始化和依赖装配
2. `domain`
   负责定义系统内部的数据模型和核心抽象
3. `application`
   负责系统流程编排和模块协作
4. `infrastructure`
   负责对接 DeepStream、GStreamer、JSON、MQTT、Kafka、Web 等外部依赖
5. `optimization`
   负责性能和稳定性策略
6. `shared`
   放通用基础能力
7. `adapters`
   负责边界适配和解耦

## 4. 每个目录职责说明

### 4.1 根目录

#### `README.md`

项目总说明，建议包含：

- 项目背景
- 系统架构图
- 快速启动方式
- 目录说明
- 常见问题

#### `requirements.txt`

Python 依赖列表。

#### `.env.example`

环境变量样例，便于配置 MQTT、Kafka、Web 端口、日志级别等。

#### `pyproject.toml`

统一项目元信息和工具配置，例如格式化、测试、静态检查。

---

### 4.2 `docs/`

用于存放项目文档，不参与主业务逻辑。

- `architecture.md`
  放系统架构说明
- `deployment.md`
  放部署步骤和环境要求
- `benchmark.md`
  放性能测试方法和结果
- `interview_notes.md`
  放适合面试表达的项目亮点整理

---

### 4.3 `configs/`

用于统一管理配置，避免把参数硬编码到 Python 文件中。

#### `configs/app/`

放业务层配置，供 Python 主控读取。

- `app.yaml`
  总配置，例如日志级别、运行模式、是否启用 Web、是否启用优化策略
- `streams.yaml`
  视频源列表，例如 RTSP 地址、名称、启停状态
- `output.yaml`
  输出目标配置，例如 JSONL、MQTT、Kafka 的开关和参数

#### `configs/deepstream/`

放 DeepStream 强相关配置。

- `infer_primary_yolo.txt`
  `nvinfer` 的主检测配置
- `tracker_iou.yml`
  跟踪器配置
- `streammux.yaml`
  多路批处理、超时等配置

#### `configs/logging/`

- `logging.yaml`
  日志格式、级别和输出位置

---

### 4.4 `models/`

放模型部署产物，不放训练代码。

- `yolov8n.onnx`
  从 PyTorch 导出的中间模型
- `yolov8n.engine`
  TensorRT 引擎文件
- `labels.txt`
  类别标签
- `calibration.cache`
  INT8 量化时使用的校准缓存

说明：

- `.engine` 文件通常建议在目标设备上生成
- 不建议把训练过程和训练脚本放进这个项目主体里

---

### 4.5 `custom_libs/`

放必须使用 C/C++ 的自定义插件。

本项目中，这一层主要用于：

- DeepStream YOLO 自定义输出解析
- 与 `nvinfer` 紧耦合的高性能后处理

建议保持这一层“小而硬”，不要把大量业务逻辑写进 C++。

---

### 4.6 `scripts/`

放辅助脚本，不进入主业务包。

- `export_onnx.py`
  导出 ONNX
- `build_engine.py`
  构建 TensorRT engine
- `run_local.ps1`
  本地启动脚本
- `benchmark.py`
  性能测试脚本

这类脚本的特点是“服务于工程过程”，不是项目运行主链路的一部分。

---

### 4.7 `tests/`

用于测试项目。

- `unit/`
  测纯 Python 逻辑，例如配置解析、结果格式化、优化策略判定
- `integration/`
  测模块协作，例如输出模块与 application 层联动
- `fixtures/`
  放测试输入样本，例如模拟检测结果、示例配置文件

---

### 4.8 `src/app/`

主业务代码目录。

#### `main.py`

程序入口，只负责启动，不堆叠复杂逻辑。

#### `bootstrap.py`

负责：

- 加载配置
- 初始化日志
- 创建核心服务对象
- 装配依赖关系

#### `settings.py`

统一配置读取和配置校验。

建议所有模块都通过这里获取配置，而不是各自直接读取 YAML。

## 5. 业务分层设计

### 5.1 `domain/`

这一层放项目最稳定、最抽象的业务模型，不依赖 DeepStream、Flask、MQTT、Kafka。

建议内容：

- `entities.py`
  核心实体，例如 `Detection`、`Track`、`FrameResult`、`StreamState`
- `value_objects.py`
  值对象，例如 `BoundingBox`、`Resolution`、`Timestamp`
- `enums.py`
  枚举定义，例如流状态、输出类型、告警级别
- `constants.py`
  通用常量

设计原则：

- 这一层只表达“系统内部有什么”
- 不表达“这些数据从哪里来”或“要发到哪里去”

---

### 5.2 `application/`

这一层负责系统流程编排，是“系统大脑”，但不直接操作底层 SDK 细节。

建议内容：

- `orchestrator.py`
  总调度器，负责组织系统启动、关闭、状态同步
- `pipeline_service.py`
  面向业务地控制 pipeline 生命周期
- `result_service.py`
  负责检测结果流转、格式化调用和输出分发
- `health_service.py`
  负责健康状态聚合

设计原则：

- 这一层只调用接口和服务
- 不直接写 DeepStream probe 细节
- 不直接写 Web 处理代码

---

### 5.3 `infrastructure/`

这一层负责对接外部依赖，是项目中变化最多的一层。

#### `infrastructure/pipeline/`

负责 DeepStream/GStreamer 主链路。

- `builder.py`
  构建 pipeline
- `manager.py`
  管理启停、重连、异常恢复
- `probes.py`
  管理 pad probe 与元数据回调
- `source_factory.py`
  生成 RTSP/file source bin

#### `infrastructure/inference/`

负责对推理结果进行基础解析和格式整理。

- `meta_parser.py`
  从 `NvDsBatchMeta` 提取检测结果
- `tracker_parser.py`
  提取 tracker 信息
- `formatter.py`
  把底层元数据整理成领域对象

#### `infrastructure/monitoring/`

负责系统运行状态采集。

- `gpu_monitor.py`
  建议优先兼容 Jetson 的 `tegrastats`
- `fps_meter.py`
  统计 FPS
- `latency_monitor.py`
  统计端到端延迟

#### `infrastructure/output/`

负责对外输出结构化结果。

- `json_writer.py`
  写入 JSONL
- `mqtt_publisher.py`
  发布到 MQTT
- `kafka_publisher.py`
  发布到 Kafka

#### `infrastructure/web/`

负责 Web 展示层实现。

- `api.py`
  HTTP 接口
- `websocket_server.py`
  推送实时结果和状态
- `static/`
  前端静态资源

设计原则：

- 基础设施层只负责“接入”与“输出”
- 不负责做系统策略决策

---

### 5.4 `optimization/`

专门放优化与稳定性策略，避免把调优逻辑混进 pipeline 构建代码里。

建议内容：

- `fps_controller.py`
  根据 GPU 负载、延迟、队列情况控制降帧或恢复
- `backpressure_controller.py`
  负责堆积保护和背压控制
- `load_shedder.py`
  在系统压力过高时进行丢帧或降载处理
- `policy.py`
  定义各类策略阈值和决策规则

设计原则：

- 策略与执行分离
- 先有规则，再由 application 层决定何时调用

---

### 5.5 `shared/`

放全项目都能复用的基础能力。

- `logger.py`
  统一日志封装
- `exceptions.py`
  自定义异常
- `time_utils.py`
  时间处理
- `file_utils.py`
  文件相关工具

说明：

- 只放真正通用的能力
- 不要把业务逻辑借道塞进 `shared`

---

### 5.6 `adapters/`

放边界适配逻辑，帮助不同层之间解耦。

- `config_loader.py`
  把 YAML、环境变量转换为内部配置对象
- `event_bus.py`
  提供轻量事件分发能力，降低模块直接依赖

适用场景：

- `pipeline` 检测到结果后，不直接调用 `web` 或 `mqtt`
- 而是先发布内部事件，再由订阅者消费

---

## 6. 推荐命名方式

### 6.1 文件命名

统一采用 `snake_case`。

示例：

- `meta_parser.py`
- `json_writer.py`
- `fps_controller.py`
- `pipeline_service.py`

不要使用：

- `test1.py`
- `main_v2.py`
- `util.py`
- `common.py`

---

### 6.2 类命名

统一采用 `PascalCase`。

示例：

- `PipelineManager`
- `ResultService`
- `GpuMonitor`
- `FrameResult`

---

### 6.3 命名规则建议

- 目录名用名词
- 服务编排类使用 `service`
- 生命周期和资源控制类使用 `manager`
- 策略控制类使用 `controller`
- 工厂类使用 `factory`
- 数据模型使用 `entity` 或 `value object`
- 输出类使用 `writer` 或 `publisher`

推荐命名示例：

- `orchestrator.py`
- `pipeline_service.py`
- `result_service.py`
- `manager.py`
- `source_factory.py`
- `mqtt_publisher.py`

---

## 7. 解耦原则

为保证项目后续容易扩展，建议坚持以下原则：

1. `domain` 不依赖基础设施层
2. `application` 不直接操作底层 SDK
3. `pipeline` 不直接依赖 Web、MQTT、Kafka
4. `optimization` 不直接改写底层对象内部状态，尽量通过服务接口驱动
5. 所有配置从统一入口加载，不允许散落读取
6. 输出模块统一消费领域对象，不直接耦合 DeepStream 原始元数据

---

## 8. 为什么这套结构适合面试

这套结构的优势在于它既能体现工程能力，也方便表达。

面试时可以概括为：

- `domain`
  定义系统内部的核心数据对象
- `application`
  负责主流程编排
- `infrastructure`
  对接 DeepStream、输出通道和 Web
- `optimization`
  负责性能调优与稳定性控制
- `custom_libs`
  只保留必须使用 C++ 的高性能插件

这一表述方式能体现你不是简单堆代码，而是在做可维护、可扩展的工程设计。

---

## 9. 落地建议

如果按实现优先级推进，建议顺序如下：

1. 先完成 `pipeline + meta_parser + json_writer`
2. 再补 `application` 层编排与统一配置
3. 然后加入 `monitoring` 和 `optimization`
4. 最后增加 `web`、`mqtt`、`kafka` 等扩展能力

这样可以先跑通主链路，再逐步增强工程化能力，风险更低，也更容易排查问题。
