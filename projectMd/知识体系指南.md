## 一、GStreamer 与 DeepStream 基础

### 1.1 GStreamer 是什么

GStreamer 是一个**多媒体处理框架**，它的核心思想是：把音视频处理的每一步都抽象成独立的元件 (element)，然后像搭积木一样把它们串成流水线 (pipeline)。

**类比**：水管工。每个 element 是一段水管，数据（水）从源头流到终点，中间经过各种处理——过滤器、分支、合并。

```
┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
│ 水源  │───→│ 过滤  │───→│ 加热  │───→│ 出水  │
│filesrc│    │parse │    │decode│    │sink  │
└──────┘    └──────┘    └──────┘    └──────┘
```

### 1.2 核心概念


| 概念         | 含义                                                   | 你的项目里对应的                                     |
| ------------ | ------------------------------------------------------ | ---------------------------------------------------- |
| **Element**  | 流水线上的一个处理单元                                 | `rtspsrc`, `nvinfer`, `nvdsosd` 每个都是一个 element |
| **Pad**      | Element 的输入/输出接口，分`sink`(进口) 和 `src`(出口) | `nvinfer` 的 sink pad 接收数据，src pad 输出结果     |
| **Bin**      | 包含多个 element 的容器，本身也是一个 element          | 你的整个 DeepStream pipeline 就是一个 bin            |
| **Pipeline** | 最顶层的 bin，管理所有 element 的状态和时钟            | `Gst.Pipeline.new("app-name")`                       |
| **Bus**      | 消息总线，element 通过 bus 向应用程序发通知            | `manager.py` 里的 `_on_bus_message`                  |
| **Probe**    | 探针，可以挂在 pad 上拦截经过的数据                    | 你挂在`primary-infer:src` 的 buffer probe            |

### 1.3 Pad 的类型

**Static Pad（静态 Pad）**：element 创建时就有的 pad。比如 `nvinfer` 有一个 `sink` 和 `src`。

**Request Pad（请求 Pad）**：需要显式向 element "索要"的 pad。比如 `nvstreammux` 每增加一路输入就要 `get_request_pad(f"sink_{i}")`。

**Dynamic Pad（动态 Pad）**：element 运行时才创建的 pad。比如 `rtspsrc` 一开始没有 src pad，等 RTSP 握手成功后动态创建，此时触发 `pad-added` 信号。

你项目里的代码对应：

```python
# builder.py — 这三种 pad 都有处理

# Static pad: 直接 link
source_element.link(target_element)

# Request pad: streammux 的 6 个 sink pad
streammux.get_request_pad(f"sink_{index}")

# Dynamic pad: rtspsrc 的动态 src pad
element.connect("pad-added", self._on_dynamic_pad_added, ...)
```

你的 `builder.py` 构建的是这样一个链路：


gpu加速？

### 1.5 DeepStream 的核心 Element


| Element         | 作用                                  | 硬件加速 |
| --------------- | ------------------------------------- | :------: |
| `nvv4l2decoder` | H.264/H.265 → NV12 (调用 NVDEC 硬件) |    ✅    |

## 二、视频编解码与色彩空间

### 2.1 H.264 → YUV → RGB 这条链路

**nvstreammux如何实现的多路帧合批 + resize + 帧同步

```
RTSP 流 (H.264 编码的 bitstream, 压缩率 ~100:1)
    │
    ▼ rtph264depay + h264parse         ← 解封装 + 语法解析
裸 H.264 NAL Units
    │
    ▼ nvv4l2decoder (NVDEC 硬件解码)   ← Jetson 专用硬件模块
NV12 (YUV 4:2:0, DMA buffer in GPU memory)
    │
    ▼ nvstreammux                       ← resize 640×640 + 6路合并
NV12 batch (6 × 640 × 640)
    │
    ▼ nvinfer (内部 TensorRT)           ← NV12→RGB + ÷255 归一化
RGB float [0,1] → YOLOv8 推理
```

### 2.2 NV12 / YUV 是什么

**为什么视频不用 RGB**：RGB 三个通道等分辨率，数据量大。人眼对亮度（Y）敏感、对颜色（UV）不敏感，所以视频压缩时把颜色降采样。

```
YUV 4:2:0 (NV12 就属于这种):
  Y 平面: 分辨率 = 图像分辨率 (640×640)  ← 亮度, 每个像素一个值
  UV 平面: 分辨率 = 图像的一半 (320×320) ← 颜色, 每 2×2 的像素块共享一组 UV

数据量对比:
  RGB:  640×640×3 = 1,228,800 字节
  NV12: 640×640×1 + 320×320×2 = 409,600 + 204,800 = 614,400 字节
  节省了 50%
```

NV12 的内存布局：

```
[Y Y Y Y ... 640×640 个 Y] [U V U V ... 320×320 对 UV]
 └── Y plane ──────────────┘ └── UV plane (interleaved) ──
```

> "视频流是 H.264 编码的，通过 NVDEC 硬件解码成 NV12 格式。NV12 是 YUV 4:2:0 的一种排列——Y 平面全分辨率保存亮度信息，UV 平面半分辨率保存颜色信息。相比 RGB，同分辨率下数据量减半，而且解码器直接输出 GPU DMA buffer，后续推理环节零拷贝。"

### 2.3 NVDEC 和 NVENC 是什么

Jetson AGX Orin 芯片上除了 GPU（负责 CUDA 计算和 TensorRT 推理），还有独立的**硬件编解码模块**：


| 模块  | 作用                         | 解码/编码能力                   |
| ----- | ---------------------------- | ------------------------------- |
| NVDEC | 硬件解码 H.264/H.265 → NV12 | AGX Orin: 最多 6 路 4K 同时解码 |
| NVENC | 硬件编码 NV12 → H.264/H.265 | AGX Orin: 最多 4 路 4K 同时编码 |

**为什么用硬件编解码而不是 GPU 算**：专用硬件比 GPU 软件解码快 10 倍以上，且几乎不占用 CUDA 核心（GPU 可以专心做推理）。

> "Jetson AGX Orin 有独立的 NVDEC 和 NVENC 硬件模块，解码和编码不占用 GPU 的 CUDA 核心。我的 6 路 RTSP 全部走 NVDEC 解码，推理完成后走 NVENC 编码推流。GPU 只做推理，视频处理交给专用硬件。这是边缘端做多路视频最高的效率方案。"

## 三、TensorRT 推理优化

### 3.1 PyTorch → ONNX → TensorRT 全链路

"模型怎么部署到 Jetson 上的？"

```
训练:   PyTorch .pt         ← 任意机器训练
         │ torch.onnx.export()
         ▼
中间:   ONNX .onnx           ← 框架无关的模型描述文件 (计算图)
         │ trtexec (TensorRT 编译器)
         ▼
部署:   TensorRT .engine     ← 针对目标 GPU 优化的可执行文件
```

### 3.2 TensorRT 做了什么

TensorRT 不能直接"跑"模型——它是**编译器**，把 ONNX 描述的通用计算图转换成针对特定 GPU 优化过的指令序列。

```
输入 ONNX 图                            优化后的 TRT Engine
─────────────────                       ──────────────────
Conv + BN + ReLU  (3 个算子, 3 次显存读写)  → 融合成 1 个 CBR 算子
LayerNorm + Add + Activation               → 横向融合
1×1 Conv stride 2                          → 替换为更高效的等价算子
FP32 权重                                   → FP16 / INT8 量化
```

> "TensorRT 本质是一个推理优化编译器。它把 ONNX 模型的计算图做算子融合（把 Conv+BN+ReLU 合并成一个 kernel）、用更高效的等价算子替换、根据目标 GPU 的 SM 架构选择最优 kernel 实现。编译产物 .engine 文件只能在同一款 GPU 上运行——我的必须在 Jetson AGX Orin 上编译，因为 engine 内嵌了 SM 8.7 的指令。"

### 3.3 FP16 vs FP32 vs INT8 深度剖析

```
FP32 (float32, 4 字节):
  ┌──────┬──────────┬───────────────────────┐
  │ sign │ exp 8bit │ mantissa (fraction) 23bit │
  │  1   │    8     │          23            │ = 32 bit
  └──────┴──────────┴───────────────────────┘
  范围: ±3.4×10³⁸, 精度: 约 7 位有效数字
  显存: 每百万参数 ≈ 4 MB

FP16 (float16, 2 字节):
  ┌──────┬──────────┬──────────────┐
  │ sign │ exp 5bit │ mantissa 10bit │
  │  1   │    5     │      10       │ = 16 bit
  └──────┴──────────┴──────────────┘
  范围: ±65504, 精度: 约 3 位有效数字
  显存: 每百万参数 ≈ 2 MB

INT8 (int8, 1 字节):
  范围: -128 ~ 127 (或 0 ~ 255)
  显存: 每百万参数 ≈ 1 MB
```

**为什么 FP16 精度损失极小**：

神经网络的权重通常在 [-1, 1] 范围内。FP16 的尾数 10 位能表示约 3 位十进制精度，对权重来说足够了。

真正影响精度的是**激活值**——中间层输出可能超出 FP16 范围（>65504 会溢出为无穷大）。解决方法是 loss scaling（训练时）和仔细量化（推理时）。

```
FP16 精度损失的来源:
  1. 梯度累积 (训练时有, 推理时没有) → ✅ 推理时不影响
  2. 激活值溢出               → ⚠️ 需检查中间层数值范围
  3. 舍入误差累积              → 对 80 类分类/检测几乎无可见影响
```

**INT8 为什么需要校准**：（量化和反量化）

INT8 把浮点数映射到 256 个整数值。映射公式是：

```
INT8_value = round(FP32_value / scale) + zero_point

scale 和 zero_point 怎么定？→ 校准 (calibration):
  - 跑 500-1000 张代表性图片
  - 统计每一层输出的 min/max 值分布
  - 根据分布确定最优的 scale
  - 校验数据集必须和线上场景一致
```

> "FP32 是训练精度，FP16 是部署的默认选择——两字节存一个数，显存直接减半，TensorRT 的 FP16 kernel 比 FP32 快 30-80%。INT8 更激进，一字节存一个数，但需要校准数据集统计每层的数值分布。YOLOv8n 只有 3M 参数，

### 3.4 trtexec 参数详解

```bash
/usr/src/tensorrt/bin/trtexec \
    --onnx=models/yolov8n.onnx \
    --saveEngine=models/yolov8n.engine \
    --fp16 \
    --workspace=2048 \          # 编译时可用显存 (MB), 越大策略搜索越充分
    --optShapes=input:6x3x640x640 \   # ★ 最优 shape, TRT 针对此做 kernel 选择
    --minShapes=input:1x3x640x640 \   # shape 范围下限
    --maxShapes=input:6x3x640x640     # shape 范围上限, 超出运行时报错
```

`optShapes` 是 TensorRT 的核心优化点：编译器会针对这个 shape 做 kernel 选择和内存分配，运行时 shape 越接近 optimal 性能越好。

> "TensorRT engine 构建时最关键的是指定 `--optShapes`，它告诉编译器运行时最常出现的 batch size。我把 optShapes 设成 6×640×640——正好是 6 路视频合批的推理尺寸。TensorRT 会针对这个 shape 选最优的卷积实现、规划显存布局，运行时在这个 shape 下性能最好。min 和 max 定义了 shape 的有效范围，超出会直接报错。"

## 四、YOLOv8 模型架构

### 4.1 整体结构

```
输入: (B, 3, 640, 640) RGB

┌──────────────────────┐
│    Backbone          │  CSPDarkNet — 提取图像特征
│    (卷积 + C2f 模块)  │  逐层下采样: 640→320→160→80→40→20
│                      │
│    特征图尺寸:        │  P3 (80×80×128)   ← 检测小目标
│    P3, P4, P5        │  P4 (40×40×256)   ← 检测中目标
└──────────┬───────────┘  P5 (20×20×256)   ← 检测大目标
           │
           ▼
┌──────────────────────┐
│    Neck (PAN-FPN)    │  特征金字塔 — 融合浅层细节和深层语义
│    自上而下 + 自下而上 │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│    Head (Decoupled)  │  三个检测头，每个 grid cell 预测:
│                      │  4(bbox) + 1(obj_conf) + 80(class_conf) = 85维
│    输出:              │
│    output0: (B,85,80,80)   ← stride 8
│    output1: (B,85,40,40)   ← stride 16
│    output2: (B,85,20,20)   ← stride 32
└──────────────────────┘
```

### 4.2 Anchor-Free 检测原理

YOLOv5 和之前的版本是**anchor-based**：预定义一组 anchor box（不同长宽比的矩形框），模型预测相对于 anchor 的偏移量。

YOLOv8 是**anchor-free**：每个 grid cell 直接预测一个目标中心点和框的宽高。

```
Anchor-Based (YOLOv5):                Anchor-Free (YOLOv8):
预定义: [宽1,高1], [宽2,高2], ...     不需要预定义 anchor
预测: Δx, Δy, Δw, Δh (相对于 anchor)  预测: cx, cy, w, h (直接值)
NMS 前 decodes 多一次乘法             更简洁，框的数量更少（NMS 更快）
```

**你的 custom parser .so 做的就是这件事**：从 `(B, 85, grid_H, grid_W)` 的三维张量中逐格解析出 bbox 坐标（归一化的 cx/cy/w/h → 像素坐标 left/top/width/height），做置信度过滤和 NMS 去重。

### 4.3 多尺度检测头

```
stride 8 (80×80 grid):  感受野小 → 检测小目标 (远处的人, 小物体)
stride 16 (40×40 grid): 感受野中 → 检测中目标
stride 32 (20×20 grid): 感受野大 → 检测大目标 (近处的车)
```

每个 grid cell 覆盖原图的一个区域：stride 8 的 cell 覆盖 8×8 像素区域，stride 32 的 cell 覆盖 32×32 像素区域。

> "YOLOv8 是 anchor-free 架构，三个检测头分别用 stride 8/16/32 对应小/中/大目标。每个 grid cell 预测 85 维——4 个 bbox 坐标、1 个 objectness 置信度、80 个类别分数。我的 custom parser 从三个检测头的 raw tensor 中遍历每个 grid cell，解码 bbox 坐标、过滤低置信度、跨三个 head 做全局 NMS 去重。这个 parser 必须用 C++ 写，因为 DeepStream 的 nvinfer 只认 .so 动态库。"

### 4.4 IoU / NMS 详解

**IoU (Intersection over Union)**：

```
         ┌────────────────────┐
         │      框 B          │
         │                    │
         │   ┌──────────┐     │
         │   │ 交集      │     │
         │   │          │     │
         │   └──────────┘     │
         │      框 A          │
         └────────────────────┘

IoU = 交集面积 / 并集面积
    = A∩B / (A + B - A∩B)

IoU = 1.0: 完全重合
IoU = 0.5: 一半重合
IoU = 0.0: 完全分离
```

**NMS (Non-Maximum Suppression, 非极大值抑制)**：

同一类别的目标可能被多个检测框同时"命中"——比如一辆车被三个不同尺度的检测头各产生一个重叠框。NMS 的作用是去重：

```
算法:
  1. 按置信度排序所有框
  2. 取置信度最高的框 A
  3. 遍历剩余框, 如果和 A 的 IoU > 阈值 (如 0.45) → 删除
  4. 取下一个未被删的最高置信度框, 重复 2-3
  5. 直到没有剩余

输出: 每个目标只剩一个最准确的框
```

> "IoU 是交并比，衡量两个框的重叠程度。NMS 是非极大值抑制，用贪心算法去重——每次选置信度最高的框，把和它 IoU 超过阈值的都删掉，然后取下一个最高的。阈值设 0.45 是我实测的最优值——太高去重不彻底，太低会误删不同但挨得近的目标。"

## 五、CUDA 编程基础

### 5.1 CPU vs GPU 架构差异

```
CPU (12 个大核)                      GPU (2048 个小核)
─────────────────                    ─────────────────
每个核: 复杂, 3-5 GHz                每个核: 简单, 1.3 GHz
擅长: if/else, 分支预测, 乱序执行    擅长: 大量完全相同的简单计算
线程切换: 操作系统调度, 慢            线程切换: 硬件调度, 零开销
内存: 大容量 DDR (32 GB)             显存: HBM/GDDR (8-64GB)
缓存: 大 (L1 64KB, L2 512KB)        缓存: 小但多 (每个 SM 有 shared memory)
```

**Jetson AGX Orin 特殊之处 — 统一内存**：

x86 上 CPU DDR 和 GPU 显存是物理分开的，数据必须通过 PCIe 总线拷贝：

```
x86:  CPU DDR ←──── PCIe (16-32 GB/s) ────→ GPU 显存

Jetson: CPU + GPU 共享同一块 LPDDR5 物理内存
        → .to("cuda") 实际上是零拷贝（改指针标记）
        → 这也是你项目可以全程 DMA buffer 不经过 CPU 的前提
```

### 5.2 CUDA 执行模型

```cuda
// 从 C++ 代码调用 — "启动一个 kernel 函数，在 GPU 上并行执行"
my_kernel<<<grid, block, shared_mem, stream>>> (args);
//         │      │
//         │      └── blockDim: 每个 block 里有多少 thread (最多 1024)
//         └── gridDim:   有多少个 block
```

```
Grid  (整个计算任务)
 ├── Block 0  (映射到一个 SM 上执行)
 │    ├── Thread 0 ─ Thread 1 ─ ... ─ Thread 31  (一个 Warp, 32 线锁定步)
 │    ├── Thread 32 ─ Thread 33 ─ ... ─ Thread 63
 │    └── ...
 ├── Block 1  (映射到另一个 SM)
 │    └── ...
 └── Block N
```

**Warp — GPU 的底层调度单位**：32 个线程锁定步骤同时执行同一条指令。如果一个 warp 里的线程走了不同的分支（if/else），GPU 必须串行执行两个分支——这叫 warp divergence，会降低效率。

**Occupancy**：一个 SM 上同时活跃的 warp 数量。Occupancy 越高，SM 越能在某些 warp 等待访存时切换到另一个 warp 执行（latency hiding）。

### 5.3 GPU 内存层次

```
最慢/最大         最快/最小
───────────────────────────────────────→
Global Memory  →  L2 Cache  →  Shared Memory  →  Register
(显存, GB级)      (几MB)       (每个 SM 128KB)    (每 thread 255个)
延迟: ~500 cycles             延迟: ~20 cycles    延迟: 0 cycles
所有 thread 共享              同一 block 共享      每个 thread 私有
```

**Shared Memory 的使用场景**：如果一个数据要被同一个 block 里的多个线程反复读取（比如卷积的权重），就加载到 shared memory，比反复从 global memory 读快 20+ 倍。

**Coalesced Memory Access (合并访存)**：GPU 的 global memory 最小读单位是 128 字节。如果相邻的 32 个线程同时访问连续的 32 个 float（128 字节），GPU 只发一次内存请求——这就是合并访存。如果随机访问，一次读 32 个随机位置，GPU 可能需要 32 次请求——慢 32 倍。

## 六、C++ 高性能模块

### 6.1 Python GIL 问题

**GIL (Global Interpreter Lock)**：Python 解释器在同一时刻只允许一个线程执行 Python 字节码。即使你有 12 核 CPU，多线程 Python 也只能用 1 个核。

```
你的项目受 GIL 影响的点:
  主线程跑 GStreamer 事件循环 (C 代码, 释放 GIL ✓)
  主线程 probe 回调 ._on_probe_buffer() (Python 代码, 持有 GIL ✗)
  
  6 路 × 30 fps = 每秒 180 次 Python 回调
  → 每次回调期间, 其他 Python 线程 (包括 Web Dashboard) 全部等待
```

**解决方案**：把 probe 回调从 Python 移到 C++（AGX.md 模块二）。C 代码不持有 GIL，且可以直接操作 C struct 字段，省掉 Python 对象的创建和属性查找。

**面试怎么讲**：

> "Python GIL 让多线程的并行性大打折扣。我的 probe 回调在 Python 里每秒被调用 180 次，每次遍历 GLib 链表、做类型转换、访问属性——不仅慢，还阻塞了 Web Dashboard 的响应。我把回调整个搬到了 C++ 里，C 代码不持有 GIL，直接操作 NvDsBatchMeta 的 C struct 字段，点号访问变成指针解引用。这个是边缘端 Python 系统的标准优化手段。"

### 6.2 Lock-Free Ring Buffer 原理

面试最喜欢问的无锁数据结构。核心思想：

```
传统有锁队列:
  push() { lock(); write; unlock(); }   ← 每次 push/pop 都要争锁
  pop()  { lock(); read;  unlock(); }

Lock-Free Ring Buffer (SPSC):
  - 只有一个生产者写 write_pos → 永远没人跟它争
  - 只有一个消费者写 read_pos  → 永远没人跟它争
  - 写操作之间的 happens-before 关系靠 atomic 的 release/acquire 内存序保证
```

**为什么单生产者单消费者 (SPSC) 能无锁**：

```
关键洞察: write_pos 只被生产者修改, read_pos 只被消费者修改

push() 流程:
  1. 读 write_pos (自己写的) 和 read_pos (别人写的, 用 acquire 保证读到最新值)
  2. if write - read < capacity: 写入 buffer[write & mask] = item
  3. write_pos += 1  (release — 确保步骤2的数据在步骤3之前对所有 CPU 可见)

pop() 流程:
  1. 读 read_pos (自己写的) 和 write_pos (别人写的, 用 acquire)
  2. if read < write: item = buffer[read & mask]
  3. read_pos += 1   (release)

关键: 没有锁, 没有 compare-and-swap, 没有忙等待 — 纯原子读/写
```

**Cache Line 和 False Sharing**：

CPU 缓存的最小单位是 cache line（通常 64 字节）。如果两个不同线程频繁修改的两个变量落在同一个 cache line，即使它们互不影响，CPU 也会不断地在这两个核之间搬整行数据——这就是 false sharing。

```
无对齐:
  ┌─ cache line (64B) ───────────────────────────────┐
  │ write_pos (8B) │ read_pos (8B) │ 其他数据...      │
  └───────────────────────────────────────────────────┘
  producer 写 write_pos → cache line 被标记为 "脏"
  → consumer 读 read_pos → 同一行被拉回, 覆盖 producer 的写 → 乒乓

对齐后 (alignas(64)):
  ┌─ cache line 0 ─────┐ ┌─ cache line 1 ─────┐
  │ write_pos (8B) │...│ │ read_pos (8B) │...│
  └─────────────────────┘ └─────────────────────┘
  producer 只改 line 0, consumer 只改 line 1 → 互不干扰
```

> "我写的 ring buffer 是 SPSC 模型——write_pos 只被生产者改、read_pos 只被消费者改，所以不需要锁。用 release/acquire 内存序保证数据写入 happens-before 指针更新，消费者一定能看到完整的数据。四个原子变量各自用 alignas(64) 独占一根 cache line，消除 false sharing。这个在面试里可以展开讲 memory order 的四个级别——relaxed、acquire、release、seq_cst，以及它们在 ARM 和 x86 上的实际差别。"

### 6.3 memory_order 四层详解

```cpp
// 从最弱到最强
memory_order_relaxed   : 只保证原子性, 不保证顺序。计数器用这个。
memory_order_acquire   : 读操作, 确保之后的读/写不会重排到这之前。
                         相当于: "读了后面才能动"
memory_order_release   : 写操作, 确保之前的读/写不会重排到这之后。
                         相当于: "前面的写完了才能放行"
memory_order_seq_cst   : 全局统一顺序, 最安全但最慢。默认值。

// Ring Buffer 里的用法:
// push: 数据写入 buffer_ → release 写 write_pos_ → consumer 用 acquire 读 write_pos_
// acquire/acquire 配对保证: consumer 看到 write_pos_ 更新时, 一定能看到 buffer_ 里的数据
```

**面试怎么讲（进阶）**：

> "x86 上 acquire/release 基本是免费的——x86 的 TSO 模型天然保证 load-acquire 和 store-release 不需要额外 fence 指令。ARM（包括 Jetson）上 release store 会编译出 `stlr` 指令，acquire load 会编译出 `ldar` 指令，有少量开销但远小于锁。所以这套设计在 Jetson 上也能高效运行。"

### 6.4 共享内存 IPC

```cpp
// 推理进程 (生产者):
shm_open("/deepstream_results", O_CREAT | O_RDWR, 0666);
ftruncate(fd, sizeof(RingBuffer));       // 设置共享内存大小
void* addr = mmap(nullptr, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
new (addr) RingBuffer();                 // placement new — 在共享内存上构造对象

// Web 进程 (消费者):
shm_open("/deepstream_results", O_RDONLY, 0666);
void* addr = mmap(nullptr, size, PROT_READ, MAP_SHARED, fd, 0);
// 直接读 addr 上的 RingBuffer 数据 — 两个进程看到同一块物理内存
```

**为什么比 `multiprocessing.Queue` 快 50 倍**：

```
multiprocessing.Queue:
  push() → pickle.dumps(obj) → pipe.write() → kernel → pipe.read() → pickle.loads()
  序列化 + 2 次内存拷贝 + 内核态切换
  延迟: 50-200 μs

Shm Ring Buffer:
  push() → memcpy 64B → atomic store   ← 纯用户态, 一次 memcpy
  pop()  → atomic load → memcpy 64B    ← 纯用户态
  延迟: 0.1-0.5 μs
```

## 七、系统性能优化策略

### 7.1 解码瓶颈 → 硬件加速

多路视频的第一瓶颈永远是**解码**。6 路 1080p H.264 如果靠 CPU 软解，单个核满算可能连 2 路都跑不下来。

**解决方案**：NVDEC 硬件解码器。AGX Orin 的 NVDEC 是独立硅片，不占 CPU 和 GPU 的 CUDA 核心。`nvv4l2decoder` 输出直接是 GPU DMA buffer，不需要从 CPU 内存搬到 GPU 显存。

### 7.2 批处理 (Batching) 优化

nvstreammux 把 6 路独立的帧合并成 1 个 batch，让 `nvinfer` 一次性推理 6 帧。

```
不 batch (串行):
  帧1→推理→帧2→推理→帧3→推理→...     每个 kernel launch 有固定开销

batch (并行):
  [帧1 帧2 ... 帧6] → 推理 (一次 kernel launch, 同时处理 6 帧)
```

`batched-push-timeout=40000μs`（40ms）的含义：nvstreammux 等待最多 40ms 凑 batch。如果第 6 路慢了（比如 RTSP 丢包、帧到了晚），其他 5 路不等——定期 push 当前已有的帧，对没来的路填空。这是**延迟和吞吐的权衡**：

```
timeout 小 (10ms):  延迟低, 但可能经常只有 3-4 路凑齐 → GPU 利用率低
timeout 大 (80ms):  几乎每次都能凑齐 6 路, 但端到端延迟增加
```

### 7.3 背压 (Backpressure) 机制

```
生产者 (Probe 回调)                消费者 (JsonWriter)
每帧 push 到队列                 从队列 pop → 格式化 → 写磁盘
速度: 180 帧/秒                  速度: 取决于磁盘 IO (~500-2000 帧/秒)
                                 正常情况: 消费 > 生产, 队列近乎空
故障情况 (磁盘满了):               消费速度 → 0
                                 → 队列堆积 → 内存爆炸 → OOM
```

背压保护做的事：

- 监控队列深度
- 深度 > 80% → 触发 production 降速（丢帧）
- 深度 < 40% → 恢复正常

**这和 TCP 的拥塞控制的思路完全一样**——发送方根据接收方的 ACK 速度调整发送速度。

### 7.4 丢帧策略设计

三种方案和你的选择：


| 方案         | 做法                                       | 缺点                                                                               |
| ------------ | ------------------------------------------ | ---------------------------------------------------------------------------------- |
| 固定间隔跳帧 | 每 3 帧跳 1 帧                             | 如果摄像头每秒 30 帧，刚好跳掉 10 帧 → 可能和摄像头帧率产生拍频（beat frequency） |
| 队列满直接丢 | 队列长度 > N 时丢新帧                      | 系统从 "不丢帧" 突然跳到 "丢帧"，可能引起抖动                                      |
| 概率丢帧     | 根据负载计算 drop_rate, 用随机数决定是否丢 | 平滑、无固定模式、无拍频 ✅ 你的方案                                               |

你的项目用的分层结构对应面试常问的"你是怎么设计代码的？"

**依赖方向** — 一个面试可以展开的点：

```
adapters → domain ← application → infrastructure
                ↑          ↑-------------↓
            shared              optimization

规则: 内层不知道外层的存在
  - domain/ 不 import DeepStream
  - application/ 不直接 write 文件
  - infrastructure/ 可以 import domain/ 但不能 import application/
```

> "我按领域驱动设计的思想做了分层——domain 层定义核心数据模型不依赖任何框架，application 层做流程编排只调接口，infrastructure 层负责对接 DeepStream/JSON/Web 这些外部依赖。依赖方向从外向内——infrastructure 可以 import domain，但 domain 绝不知道 infrastructure 的存在。这样换推理框架（比如从 DeepStream 换到纯 GStreamer）时只改 infrastructure 层，业务逻辑不动。"

### 8.2 Pipeline Blueprint 模式

`builder.py` 的核心设计——**先构建蓝图，再做运行时实例化**：

```python
PipelineBlueprint  (纯数据对象, 可序列化, 可比较)
  ├── nodes:   6 个分支节点 + 9 个主干节点
  ├── links:   分支内链路 + 主干链路 + request pad 链路
  ├── probes:  primary-infer:src, tracker:src, osd:sink
  ├── timestamp_policy: {timestamp_mode, sync_enabled, ...}
  └── output_policy:  {enable_osd, enable_encoder, ...}

build_runtime()  → 把 blueprint 转成真正的 GStreamer element
  - 如果 GStreamer 环境不可用 (比如开发机) → 返回蓝图给测试用
  - 如果 GStreamer 环境可用 (Jetson) → 实例化真正的 element
```

> "pipeline 构建我用了蓝图模式——先收集配置、校验、组装成不可变的数据对象 (PipelineBlueprint)，再在运行时根据环境决定是否实例化成 GStreamer element。这意味着我的构建逻辑可以脱离 Jetson 独立测试——在开发机上跑单元测试，blueprint 的结构、链路、probe 点全都能验证，不需要连硬件。"

### 8.3 为什么用 Frozen Dataclass

```python
@dataclass(frozen=True)
class Detection:
    class_id: int
    class_name: str
    confidence: float
    bbox: BoundingBox
```

`frozen=True` 意味着创建后不能修改任何字段。

**为什么**：多路并发场景下，如果一个 Detection 对象被多个消费者（JSON writer + Web Dashboard + MQTT publisher）共享，不可变对象天然线程安全——你不用担心一个消费者在写、另一个在读。
