# 项目现状梳理与阶段总结

## 1. 项目最终目标

> 权威任务定义见：[最终任务定义与改造计划.md](最终任务定义与改造计划.md)。本项目不是分别维护离线 demo 和 RTSP demo，而是一套支持 file/RTSP 输入、MP4/RTSP/RTMP 输出的统一多路推理程序。

这个项目最终要做成一个运行在 Jetson AGX Orin 上的统一多路视频分析系统，能力参考 `demo_multhread_decode_infer_mulmodel`。主链路大致是：

`视频源(RTSP/本地文件) -> 硬件解码 -> 批处理 -> YOLOv8 推理 -> 跟踪 -> OSD -> 硬件编码 -> RTMP 推流/结构化结果输出`

输入可以是本地 MP4 或 RTSP。没有真实摄像头时，由本地 MP4 通过 MediaMTX/FFmpeg 模拟 RTSP，作为正式实时模式验收方式。输出可以是本地 MP4、RTSP/RTMP 和 JSONL，输入输出应可通过配置组合切换。

当前代码、文档和讨论已经把目标收敛成了分层单体架构，重点是先完成统一多路推理闭环，再考虑 INT8、增强 tracker 和更多业务输出。

如果对比早期学习文档，主目标已经从“学习型练习项目”转成了“可落地的工程项目原型”。目前代码实现更接近后者。

## 3. 目前还没实现什么

### 还没完成

- 统一入口下的 file/RTSP 输入和 MP4/RTSP/RTMP 输出组合验收。
- 8 路模拟 RTSP 的完整稳定性、重连和质量验收。
- 真正的 MP4/RTSP 输出链路验收，避免通过 `fakesink` fallback 误判成功。

### 已设计但未实现

- 更完整的 Web 控制面。
- 真正的结果异步消费队列。
- INT8 量化路线。
- 更强 tracker 路线。
- 更细的性能控制策略。

### 已有部分实现但未闭环

- `builder.py` 的 pipeline 蓝图与 runtime 规划。
- `manager.py` 的 bus 处理和状态分类。
- `orchestrator.py` 的状态汇总和控制逻辑。
- `meta_parser.py` 的兼容解析。
- Web 状态页和 debug API。
- GPU 监控与优化策略占位。

### 距离最小可用版本还缺什么

- 输入 source ID、帧号、时间戳、FPS 和丢帧规则统一。
- 结果输出异步化，避免 JSONL 写盘阻塞 probe 热路径。
- 单路 source 断流时的局部恢复，以及其余路继续运行。
- 真正的 MP4 编码和 RTSP/RTMP 推流验证。

### 距离完整 Jetson 验收还缺什么

- 多路硬件解码、`nvstreammux` request pad、动态 pad、probe 的稳定性验证。
- 8 路 MP4 和 8 路模拟 RTSP 的完整组合验收。
- 多路并发、长时间运行、断流重连和输出 sink 故障验证。

## 4. 当前项目处于什么阶段

目前更像是：**统一多路推理原型 + 两种正式输入模式已经具备入口，但统一输出和稳定性验收尚未完成**。

判断依据：

- 架构和目录已经搭起来了。
- 主链路角色已经分清。
- 测试能通过，说明基础联通可用。
- 已有 Jetson/DeepStream 运行产物，但 8 路 RTSP 模拟验收仍出现缺路和低 FPS，不能视为最终通过。

### 完成度判断

按新的最终任务口径，我会估计当前完成度约为 **65%**：统一 pipeline、模型资产和主要运行入口已经存在，但四种输入输出组合、稳定性和故障恢复还没有全部通过。

原因是：

- 工程骨架和状态联通已经完成了一大半。
- 真正决定能否落地的板端资源、真实推理、真实视频链路、稳定性和性能调优还没有完成。

## 5. 开发板结合情况

目前和开发板结合，做到的是“面向开发板设计好了”，但还没有“在开发板上验证完成”。

### 已经做了什么

- 代码里预留了硬件解码、`nvstreammux`、`pyds`、推理、跟踪、编码这些角色。
- 配置里已经按 DeepStream 方式组织模型、tracker、streammux、engine 路径。
- 架构上已经把板端能力放进 pipeline 层，而不是写成散乱脚本。

### 还没做到什么

- 没有板端实测证据证明硬件解码真的生效。
- 没有板端实测证据证明 `NvDsBatchMeta` 解析真的通了。
- 没有足够实测证据证明 8 路并发推理和 MP4/RTSP/RTMP 输出能稳定同步。
- 没有板端实测证据证明编码、推流、OSD、tracker 在 Jetson 上稳定运行。

### 上板前最先确认的事项

- JetPack / DeepStream 版本是否匹配。
- `pyds`、GStreamer、TensorRT、CUDA 是否完整。
- 模型文件、engine 文件、custom parser `.so` 是否齐全。
- RTSP / 本地视频源是否稳定。
- 先用 1 路验证统一 pipeline，再逐步扩到 4 路和 8 路组合验收。

## 6. 最终结论

- 这个项目最终要做成一套类似 `demo_multhread_decode_infer_mulmodel` 的统一多路推理系统。
- 本地 MP4 和模拟 RTSP 都是正式任务范围，不是互相替代的阶段版本。
- 当前已具备统一 source/pipeline/result 核心，但还没有完成全部输入输出组合的最终验收。
- 下一阶段最优先的 3 件事是：
  1. 统一 source ID，解决 8 路模拟 RTSP 缺路和编号错位。
  2. 完成 file/RTSP 输入与 MP4/RTSP/RTMP 输出的组合验收。
  3. 将结果输出、重连恢复和质量判定做成可重复的 8 路验收。
