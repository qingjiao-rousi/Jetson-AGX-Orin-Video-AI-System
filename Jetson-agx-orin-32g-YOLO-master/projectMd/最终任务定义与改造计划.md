# 最终任务定义与改造计划

## 1. 最终任务

同一套核心推理链路必须支持：

```text
输入：本地 MP4 或 RTSP
输出：每路独立推理 MP4、RTSP/RTMP，以及 JSONL 结构化结果
```

本地 MP4 通过 MediaMTX/FFmpeg 模拟成 RTSP，用于替代当前无法提供的真实摄像头环境。RTSP 模拟不是独立的临时 demo，而是正式验收方式。

核心链路统一为：

```text
多路输入 -> 解码 -> nvstreammux 合批 -> YOLOv8 TensorRT 推理
-> tracker -> OSD/编码 -> MP4 或 RTSP/RTMP 输出 -> JSONL/metrics 输出

视频验收默认不再依赖 2x4 合并预览。每个 source 应输出独立的 OSD 推理视频，
并在高级调试区按 `stream_id` 分别播放，用于观察检测框、track_id、误检和漏检。
合并视频仅作为可选诊断产物，不作为正式验收产物。
```

输入类型和输出类型可以组合切换，不能为本地文件和 RTSP 维护两套不同的推理实现。

## 2. 必须通过的组合

| 编号 | 输入 | 输出 | 目的 |
| --- | --- | --- | --- |
| A | 8 路本地 MP4 | 本地 MP4 + JSONL | 离线多路推理 |
| B | 8 路本地 MP4 模拟 RTSP | 本地 MP4 + JSONL | 实时输入、解码、重连和推理 |
| C | 8 路本地 MP4 模拟 RTSP | RTSP/RTMP + JSONL | 实时输出链路 |
| D | 混合 file/RTSP 配置 | MP4 或 RTSP/RTMP + JSONL | 输入输出可组合性 |

真实摄像头不是当前验收前置条件。RTSP 模拟链路稳定即可完成实时模式验收。

## 3. 当前代码判断

当前代码已经具备统一核心的主要基础：

- `SourceSettings.kind` 支持 `file` 和 `rtsp`。
- `SourceFactory` 将不同输入转换成统一的 source branch。
- `PipelineBuilder` 统一组装 mux、infer、tracker、OSD、编码和 sink。
- `PipelineManager` 负责统一启动、停止、bus 和 EOS 处理。
- `MetaParser`、`ProbeRegistry`、`Orchestrator` 和 `JsonWriter` 不区分输入类型。
- 已有本地多文件单 pipeline 和 RTSP 单 pipeline 入口。

当前主要问题不是重新设计推理流程，而是把已有能力收敛成真正统一、可组合、可验收的运行方式。

## 4. 代码改造方向

### 4.1 统一运行入口

新增通用运行入口，例如 `scripts/run_multistream.sh CONFIG OUTPUT_DIR`。输入类型由 YAML 的 `sources[].kind` 决定，输出类型由 `deepstream.output_sink` 决定。

现有 `run_multifile_inproc.sh` 和 `run_rtsp_inproc.sh` 应逐步变成参数适配器，不能继续各自维护一套 pipeline 逻辑。

### 4.2 抽象输出 sink

- `fake`：只验证推理和 JSONL。
- `file`：硬件编码后写本地 MP4。
- `rtsp` 或 `rtmp`：硬件编码后推流。
- 可选 `file_and_stream`：同一编码结果分支到文件和流。

当前 `rtmp` 使用 `flvmux + rtmpsink`，需要补充真正的 RTSP 输出方式，或明确由 MediaMTX 接收 RTMP 后提供 RTSP/WebRTC。

### 4.3 统一 source 标识

每路 source 必须同时保留配置名称、source index、`stream_id`、原始 URI、重连次数和当前状态，避免 simulator 使用 `stream3` 而推理结果使用 `stream-3` 造成验收错位。

### 4.4 结果输出解耦

JSONL/metrics 应改为有界异步输出队列，队列满时按配置丢弃旧帧并记录计数，不能阻塞 DeepStream probe 热路径。

### 4.5 运行状态和恢复

需要区分单路 source 断流、pipeline 全局 ERROR、输出 sink 故障、正常 EOS 和主进程退出。实时模式至少要验证单路断流后其他路继续运行。

## 5.1 当前状态结论

核心代码和主要验收链路已经完成。当前系统已经支持：

```text
本地 MP4 / 模拟 RTSP 输入
-> 统一多路解码、nvstreammux、TensorRT 推理、tracker、OSD
-> 独立推理 MP4 / RTMP / MediaMTX RTSP relay
-> 异步 JSONL、runtime metrics 和高级调试区
```

1/4/8 路性能基线和 10 分钟稳定性测试已完成。剩余工作主要是生产部署收尾和后续增强，不再属于核心 pipeline 重构。

## 6. 后续多模型推理要求

后续将仿照 `demo_multhread_decode_infer_mulmodel` 的处理方式，在同一套多路解码、调度和输出框架中加入新的模型进行推理。新增模型不能通过复制一套完整 pipeline 或复制一套主循环来实现。

每个模型至少需要具备独立的：

- 模型文件和版本信息；
- 输入尺寸、类别标签和置信度配置；
- TensorRT/RKNN/其他后端的推理实例；
- 后处理和类别映射；
- 模型结果与 `stream_id/frame_id/timestamp` 的关联；
- 启用、禁用和运行状态；
- 单模型耗时、FPS、错误和丢帧指标。

新增模型的结果应统一汇总到同一帧结果对象中，并保留模型来源，例如：

```json
{
  "stream_id": "stream-0",
  "frame_id": 12,
  "models": {
    "person": {"detections": [], "tracks": []},
    "helmet": {"detections": []}
  }
}
```

如果多个模型对同一目标需要融合，应单独增加 fusion 层，记录参与融合的模型、各自置信度、融合规则和最终结果，不能在 parser 或输出脚本中隐式拼接。模型扩展还必须兼容 file/RTSP 输入和 MP4/RTSP/RTMP 输出组合。

## 7. 精度与性能深化方向

混合精度量化是本项目最值得深入研究的方向之一，但不是唯一方向，也不应在没有基线和精度评估前直接切换到 INT8。

当前项目已经具备适合研究量化的条件：

- 8 路统一 batch 推理链路已经稳定；
- FP16 TensorRT engine 已完成；
- JSONL 中保留逐帧检测结果，可用于精度对比；
- runtime metrics 可记录 FPS、GPU、温度、内存和丢帧；
- 同一输入可以重复运行，便于建立 FP16/INT8 对照实验。

推荐研究顺序：

1. 固化 FP16 基线，包括 mAP/召回率、误检漏检、总 FPS、单路 FPS、功耗和温度。
2. 准备覆盖真实场景的 calibration dataset，不能只用少量样本校准。
3. 先做全 INT8 engine，检查精度和吞吐变化。
4. 对敏感层保留 FP16，对稳定层使用 INT8，形成混合精度 engine。
5. 对比不同 precision profile 在 1/4/8 路和长时间运行下的效果。

混合精度量化的研究价值在于同时优化吞吐、显存、功耗和温度，特别适合 Jetson 边缘设备。但如果 profiling 显示瓶颈主要来自解码、tracker、OSD 或 Python probe，量化不会单独解决全部问题，因此应与端到端 profiling、batch、队列和热路径优化配合进行。

量化验收至少需要记录：

- 模型精度变化：mAP、召回率、误检率、漏检率；
- 系统性能变化：总 FPS、每路 FPS、端到端帧龄和丢帧率；
- 设备资源变化：GPU 利用率、显存、功耗、温度和长期稳定性；
- 模型一致性：`stream_id/frame_id/timestamp` 和 track 行为不能因量化失效。

## 8. 最终完成标准

1. 四种输入输出组合能够按配置启动。
2. 8 路 source 全部有结果，且 source ID 可追溯。
3. MP4 输出可播放，RTMP 输出可被 MediaMTX 接收，RTSP 输出可通过 MediaMTX relay 被客户端接收；直接 RTSP 推流作为插件可用时的增强模式。
4. 推理、tracker、JSONL 和 metrics 持续工作。
5. 单路断流不会导致其他路全部停止。
6. 验收报告为 `passed`，而不是仅有输出文件或 `review`。
